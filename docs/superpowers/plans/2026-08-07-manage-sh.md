# ACP Runtime Manager Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add one safe `manage.sh` entry point for starting, stopping, testing, upgrading, and rolling back ACP without repeating manual release steps.

**Architecture:** `manage.sh` is version-controlled in the ACP repo and operates on the stable `~/Downloads/ACP` layout (overrideable with `ACP_BASE`). Runtime data remains under `shared/`; releases remain under `releases/`; the active app is `BASE/acp`. Process state uses PID files under `shared/run` and logs under `logs`. Upgrade validates a release before switching the active symlink and automatically restores the previous release if startup fails.

**Tech Stack:** Bash, Python 3/venv, SQLite backup via Python stdlib fallback, curl, optional ngrok, existing ACP Python test modules.

## Global Constraints

- Never print or commit `.env.local`, access keys, Threads tokens, `ACP_MASTER_KEY`, dashboard secrets, webhook secrets, live DBs, or generated production media.
- Never run `run.py init` against an existing live DB during upgrade; use `acp.core.db.init_db()` only.
- Tests and upgrade verification force `ACP_ADAPTER=mock` and `ACP_SOURCE=mock` to prevent live publishing/API side effects.
- `start` may run ngrok only when an ngrok URL is explicitly configured or safely derivable from an ngrok public/media URL.
- `upgrade` never force-pushes, commits, merges, or rewrites Git history.
- `rollback` switches only to a previously recorded existing release.
